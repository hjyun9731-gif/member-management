## 구현

1. `change_history_decisions` 감사 테이블을 추가한다. 원본 변경이력은 보존하고, 판정/확정·자동·보류/포함·제외·보류/근거/처리자/규칙 버전/원본 지문을 새 행으로 쌓는다.
2. 원본 지문이나 최신 판정 ID가 달라지면 관리자 판정 저장을 409로 거부한다. 저장된 판정 후 원본이 바뀌어도 실적을 자동 확정하지 않고 보류한다.
3. 과거 판정 미저장 기록과 단순 '내용 변경' 판정은 정상 실적으로 간주하지 않는다.
4. 주소·상호는 문자열 차이만으로 실제 변경을 인정하지 않는다. 최초 입력·표기·오류정정은 제외하고, 실제 변경 선택/관리자 확인 근거를 구분한다.
5. 실제 번호 간 변경은 회원 저장 전에 `actual` 또는 `correction` 사유가 필요하다. 번호 변경만으로 대폐차를 만들지 않는다.
6. 대폐차는 차종 변경을 사용하고 연식 변경을 보존한다. `포터Ⅱ/포터II` 같은 유니코드 표기 차이는 제외한다. 구조·연료만 바뀐 경우 별도 구조변경으로 기록한다.
7. 구조변경/등록이관/이전전출/말소·폐차를 별도 집계한다. 말소·폐차를 실제 사업 폐업에 자동 합산하지 않는다.
8. 변경이력대장·통계·월례보고·연도별 변경 실적이 같은 판정 서비스를 사용한다. 변경이력 연동 월례보고 항목은 오래된 수기값으로 자동집계를 덮지 않는다. 기존 수기값은 보존하고 차이를 반환한다.
9. 기존 이력 수정/삭제 API는 원본 덮어쓰기 대신 판정 기능을 안내한다. 서버 시작 및 유형 재정규화 API도 원본을 수정하지 않고 후보만 제시한다.
10. 변경이력 판정 저장 실패 시 회원 수정도 함께 롤백한다. 같은 날 실제로 되풀이된 별도 사건은 과도한 중복 제거로 누락시키지 않는다.

## 안전한 DB 대조

원본 지문 SHA256: `4ae4ccae17610156c3e9e08814aa2e5c98cc34692e448fb627c5a10088bdcc1e`.

```bash
python scripts/history_reconcile.py \
  --source '변경이력대장(1).xlsx' \
  --draft '변경이력대장_3662건_사용자기준_최종판정초안.xlsx' \
  --out review-preview
```

읽기전용 `DATABASE_URL`을 안전한 환경변수로 설정한 뒤 같은 명령에 `--connect`를 추가한다. 비밀번호를 명령 인수나 채팅에 붙이지 않는다. 접속 없이 대조하려면 `--snapshot ID포함_DB내보내기.jsonl`을 사용한다. DB 내보내기는 id, change_type, region, vehicle_number, name, before_value, after_value, change_date, receipt_date, memo, deleted_at 항목이 필요하다.

- 주소/메모의 공백이나 '호'를 지우지 않는 원본 업무 항목 대조를 수행한다.
- 원본 및 DB 양쪽이 모두 유일한 1대1 연결만 `MATCH_UNIQUE`로 인정한다.
- `MISSING`, `AMBIGUOUS`, `SOURCE_DUPLICATE`, 삭제된 DB 기록은 자동 연결하지 않는다.
- `MATCH_UNIQUE`는 연결 후보이지 업무 판정 승인이나 백업 검증을 뜻하지 않는다.
- DB 접속은 앱 startup을 import하지 않는다. PostgreSQL에서는 repeatable-read/read-only 트랜잭션과 60초 제한을 사용한다. UPDATE/INSERT/DELETE/DDL 기능은 없다.
- 원본 파일 지문이 다르면 유형 내 순번 규칙을 적용하지 않고 중단한다.

## 테스트 재현과 한계

```bash
python scripts/run_isolated_tests.py
node --check app/static/app.js
git diff --check
```

회귀 테스트는 모듈별 별도 프로세스·새 SQLite DB로 실행한다. 기존 테스트는 전역 엔진/준비 캐시와 startup 스레드를 공유하여 단일 프로세스에서 순서에 따라 스키마 충돌이 발생했다. 테스트 fixture는 startup 유지보수/기본관리자 스레드만 격리하고, 스키마 보장·마이그레이션 함수는 해당 테스트가 직접 검증한다. 운영 startup을 비활성화한 것은 아니다.

환경: Python 3.12, FastAPI 0.162.0, Starlette 1.10.0, SQLAlchemy 2.1.6, pytest 9.2.0, httpx 0.28.1. 요구사항 파일의 버전을 임의로 변경하지 않았다.

최종 전체 모듈 격리 실행: **187 passed, 1 skipped, 실패 모듈 0개**. 건너뛴 1개는 기존 PostgreSQL 전용 점검 API 테스트다. 변경이력 신규 테스트 25개를 포함하며, 기존 대리인 자격증명발급번호/대리인 이력/회원 분류/수납 기능도 전체 목록에 포함했다. 단일 프로세스 전체 실행에서는 앞서 설명한 테스트 간 상태 공유로 실패가 관찰되어, 이를 동일 조건의 통과 결과로 바꾸어 표기하지 않았다.

브라우저 실행 파일을 확보하지 못해 실제 화면 클릭 검증은 완료하지 못했다. JavaScript 문법 검사와 API→DB→집계 통합 테스트를 수행했다. 운영 PostgreSQL, Railway 배포, 백업 복구시험과 PostgreSQL 전용 점검 테스트는 아직 검증하지 못했다.

## 운영 반영 전 남은 절차

1. Railway에서 배포 서비스·프로젝트·환경·실행 커밋·자동배포 연결 브랜치 확인. 먼저 읽기전용 DB 접속 또는 필요한 컬럼/ID가 있는 내보내기 확보.
2. 읽기전용 대조로 원본행→DB ID 연결, 누락/모호/삭제/중복 건수와 실제 월별 집계를 보고. 이름이나 엑셀 순번을 DB ID로 쓰지 않는다. 회원 원장 및 폐업현황 대장과의 동일 사건 검증도 이 단계에서 수행.
3. 운영 pg_dump 전체 백업 생성, SHA256/크기/스키마·주요 테이블 수 기록. `pg_restore --list` 확인만으로 복구 검증 완료라고 하지 않는다. 별도 PostgreSQL에 실제 복구하고 회원/원본 이력/대리인/수납 데이터 행수 및 주요 합계를 검증.
4. 복구한 DB에 새 스키마와 승인된 판정만 시범 적용. 원본 지문·행수 불변, 대리인 번호 회귀, 변경이력/통계/월례보고 일치, 수기값 차이와 업무유형별 전후 수치 검증. 3,122건 보류를 임의 정상 처리하지 않는다.
5. 운영 DB에서 승인된 DB ID별 판정 계획, 예상 신규 감사기록 건수, 영향, 복구 방법을 먼저 제시. 현재 자료만으로 대량 반영 명령은 실행하지 않는다.
6. 사용자 확인 후 원격 작업 브랜치 push/PR, main 병합 및 Railway 배포 여부를 결정. 배포 시작 명령이 자동 마이그레이션을 수행하므로 **스키마 변경도 운영 DB 변경**임을 포함해 준비 상태를 보고해야 한다.
7. 적용 후 동일 대조/집계 재실행. 원본/회원/대리인 건수 보존 및 승인 범위 외 변경 0건을 확인하고 최종 보고.
